# 当前优化方向计划

Last updated: 2026-06-16

## 当前慢的根因（read-only 已确认）

### 1. `--infer-max-workers 16` 锁死客户端 fan-in（最大瓶颈）

`src/infer/backend.py:384`：

```python
max_workers = max(1, min(int(batch_size), int(self.config.max_workers), len(prompts)))
with concurrent.futures.ThreadPoolExecutor(max_workers=max_workers) as executor:
    ...
```

每个 runner（`instruction_following` / `coding` / `maths` / `longbench` pipeline）都走这条路，`--infer-max-workers 16` 直接把客户端任意时刻在途 HTTP 限制到 `<= 16`。

服务端 `src/infer/service.py:199-254` 的 50ms collect 窗口最多只能凑到 16，`--max-batch-size 1024` 不可达。

`summary-6/15.md:535-542` 自己写着：

- 1.5B 用 64
- 2.9B 用 128
- 7.2B / 13.3B 用 32

本次 sweep 全部跑成 16，是配置回退。

### 2. `--rwkv-prefill-token-budget 8192` 给 longbench 加了一刀

- ifeval: `~50 tok * 16 ~= 800`，一次过。
- human_eval: `~120 * 16 ~= 1900`，一次过。
- longbench: `~2048 * 16 ~= 32768`，至少切 4 次 prefill pass。

### 3. Pipeline chunk 屏障吃掉尾延迟

- `instruction_following/pipeline.py:113`、`coding/pipeline.py:236-279`、`longbench.py:444-478`：`chunk_i` 全完成才放 `chunk_{i+1}`，单条慢请求拖整 chunk。
- `maths/pipeline.py:323-339`：CoT stage1 全部完成后才开 stage2，跨阶段 0 重叠。

### 验算

`870 / 10min / 8 runner = ~10.9/min/runner`，平均 `5.5s/completion`。

16 in-flight 摊出来约 `88s/request`。decode 重 + 偶发长 prefill，数字对得上。没有死锁/网络问题。

## Engine / State 复用 + chunk 复用

### State 复用怎么做

RWKV-7 是递归 state（不是 KV cache），固定前缀对应固定末态。

`src/infer/state_pool.py` 里的 `StateCacheManager`（L1 RAM 16 + L2 SQLite 64）已经实现完整，但只挂在 `lightning_engine.py:145-153`，主服务路径完全没用。

落地三步：

1. `InferenceService.__init__` 接 `state_cache`，server 加 `POST /v1/prefill_prefix -> {state_hash}`，pin 住 key 防 L1/L2 淘汰。
2. `CompletionRequest` 加 `state_hash` 字段，worker 命中就用 cached 末态做 `initial_state`，跳过前缀 prefill。
3. miss 返回 `409`，让 caller 重新 prefill。绝对不能静默回退空 state，否则分数会静默错。

### Chunk 复用怎么做

#### B2 - FC system+tools 复用（单条节省最大）

BFCL v3 / tau-bench / agentbench 每轮的 system + tool definitions 完全相同（500-2000 tok）。

runner 启动时把这段送 `/v1/prefill_prefix` 拿 hash，episode 内每次 generate 只传 `state_hash + tail`（user 当轮 + assistant 起始）。

关键风险：

- hash 必须由相同 renderer 生成。
- schema 序列化任何空白/顺序差异都会 miss。

mitigation：

- 走 `src/eval/function_calling/common.py` 已经集中的 renderer。

#### B3 - avg_k 复用

ifeval `k=4`、human_eval `k=32`，现在 k 次独立 HTTP 都重新 prefill 同一 prompt。

改成 chunk 携带 `(prompt, n=N)`，引擎一次 prefill 抽 k 个。

- ifeval prefill 降到原来的 `1/4`。
- human_eval prefill 降到原来的 `1/32`。
- 解码不变（k 条 sequence 还是要走）。
- prefill 重的项收益大，decode 重的收益小。先测一发。

#### B4 - longbench by-document（缓做）

每份文档对应多个 question 才有收益。当前数据集分布不一定值得，等 B2 测完再说。

#### B5 - radix attention（缓做）

scheduler 自动检测 in-flight 共享前缀并 fork state，实施成本高。前面几条够用就别动。
